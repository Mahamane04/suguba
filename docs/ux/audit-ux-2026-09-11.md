# Audit UI/UX et plan de refonte — Suguba (11 septembre 2026)

Audit mené sur l'application réelle (serveur local, base de production en lecture), en vue
mobile 375×812, avec une session de test par rôle (secret de session jetable, comptes fictifs :
ce sont donc les écrans d'un **nouvel utilisateur**). Complété par une analyse du code des 47 pages.

Objectif fixé par l'utilisateur : que l'admin, le client, le fournisseur, le revendeur et le
client diaspora soient satisfaits par l'interface **à 90 % minimum**.

---

## 1. Constat global

L'application fonctionne, mais l'expérience n'inspire pas confiance et ne guide pas. Trois causes,
par ordre de gravité :

1. **La confiance est cassée avant même le design.** Plusieurs écrans affichent les données d'un
   compte de démonstration à la place de l'utilisateur connecté, et des promesses sans mécanisme.
2. **Chaque écran a été construit séparément.** Pas de composants communs pour les cartes, les
   en-têtes, les états vides, les champs, les messages : couleurs, tailles et tons divergent d'une
   page à l'autre.
3. **Les parcours ne sont pas pensés « tâche d'abord ».** Sur la page produit, le client ne voit ni
   le nom ni le prix sans défiler ; le tableau de bord admin empile tout sur 2 973 px.

## 3. Grille de satisfaction et estimation actuelle

Chaque rôle est noté sur 10 critères (10 points chacun) : **tâche principale réussie sans aide**,
**confiance** (aucune donnée fausse ni promesse vide), **clarté** (on sait où on est et quoi faire),
**premier usage guidé**, **rapidité** (nombre d'actions pour la tâche clé), **états vides / erreurs /
chargement soignés**, **cohérence visuelle**, **lisibilité mobile en plein soleil**, **accessibilité**
(contraste, cibles ≥ 44 px, libellés), **retour visible après chaque action**.

Estimation d'après cet audit (à re-mesurer à chaque phase avec la même grille) :

| Rôle | Estimation actuelle | Cible |
|---|---|---|
| Client (acheteur) | ~45 % | ≥ 90 % |
| Revendeur | ~45 % | ≥ 90 % |
| Fournisseur | ~45 % | ≥ 90 % |
| Admin | ~35 % | ≥ 90 % |
| Livreur | ~40 % | ≥ 90 % |
| Client diaspora | ~25 % | ≥ 90 % |

## 4. Plan de refonte de A à Z

Principe : **confiance d'abord, fondations ensuite, puis un rôle à la fois**. Chaque phase se
termine par le protocole de vérification (section 5) et une nouvelle mesure de la grille.

### Phase 0 — Confiance (bloquant, en premier)
- Supprimer la dépendance au compte démo : identité réelle via le serveur (nom, rôle, téléphone)
  pour les 12 écrans qui lisent `state.currentUser`.
- Retraits et historique revendeur sur les vraies données ; inventaire fournisseur sur les vraies données.
- Retirer promesses sans mécanisme et jargon technique (diaspora, admin, livreur).
- Masquer de la navigation les pages parrainage / défis / académie en attendant la décision.

### Phase 1 — Fondations du design system
- Composants communs : `PageHeader`, `Card`, `StatCard`, `EmptyState` (avec action), `StatusPill`,
  `Field` (texte ≥ 16 px sur mobile), `BottomSheet`, `Toast` (remplace `alert`/`confirm`),
  `Skeleton`, `Tabs`/`Chips`, `ConfirmDialog`.
- En-tête unique (logo identique partout, menu compte, sélecteur d'espace multi-rôle).
- Barre du bas par rôle, **y compris diaspora** ; bouton WhatsApp repositionné pour ne plus rien
  recouvrir (masqué là où une action fixe existe).

### Phase 2 — Client (acheteur)
- Accueil : en-tête compact, catégories, bandeau de réassurance, grille avec squelettes de chargement.
- Page produit réordonnée : galerie → nom, prix, réassurance → **barre « Commander » fixe** →
  commande en feuille par étapes (coordonnées → livraison → récapitulatif), sans `alert`.
- Confirmation et suivi : reçu clair, frise d'étapes de livraison.

### Phase 3 — Revendeur
- Accueil avec « premiers pas » (partager un premier produit, première vente) et vraies données.
- Gains : frise des commissions (en attente → disponible → versée), retrait guidé.
- Ventes : statuts lisibles, filtres, action « relancer le client ».

### Phase 4 — Fournisseur
- Accueil guidé (compléter la fiche, déposer un premier produit, ajouter des photos).
- Dépôt de produit par étapes (photos d'abord), inventaire sur les vraies données.

### Phase 5 — Client diaspora
- Vrai espace : commander pour un proche (bénéficiaire, adresse à Bamako), affichage en devise,
  paiement carte via SasPay, suivi ; barre du bas dédiée ; promesses limitées à ce qui est réel.

### Phase 6 — Admin
- Découpage en sections : **« Aujourd'hui »** (appels à passer, livraisons à assigner, retraits,
  nouveautés à vérifier), Catalogue, Réglages, Livreurs, SAV. Suppression des gadgets et du jargon.

### Phase 7 — Livreur
- Cartes de course lisibles (adresse, repère, montant à encaisser, appeler, itinéraire), validation
  du code, portefeuille.

### Phase 8 — Qualité transverse
- Accessibilité (contrastes, focus visibles, libellés, cibles ≥ 44 px), performance (images,
  poids des pages), textes simples et cohérents, états vides / erreurs / hors ligne partout.

### Phase 9 — Vérification finale
- Scénarios complets par rôle, captures mobile et ordinateur de chaque écran, nouvelle notation
  de la grille ; toute note < 90 % renvoie à une correction avant clôture.

---

## 5. Protocole de vérification (après chaque étape)

1. `npm run build` sans erreur.
2. Captures mobile (et ordinateur pour l'admin) des écrans touchés, **pour chaque rôle concerné**,
   avec des sessions de test signées par un secret jetable (jamais le vrai secret).
3. Parcours cliqué de la tâche principale, console sans erreur, requêtes sans refus inattendu.
4. Aucune écriture de test en production ; toute migration appliquée **avant** le déploiement.
5. Commit par étape, déploiement, contrôle en production, puis mise à jour de `REPRISE.md`.
